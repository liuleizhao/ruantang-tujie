# 图解 ↔ 人物：双向关系分析（人物→图解，图解→人物）

- 日期：2026-10-30
- 证据基础：
  - 语料库 `docs/corpus/softcandy/`（17 来源）与 `docs/corpus/character-patterns/`（17 来源 + ANALYSIS.md），共 34 个来源；
  - 本仓库可执行验证：`characters/芙宁娜/toyspec.json` → `chart.json` 的重建与校验（70 圈 / 1542 针 / 校验通过）；
  - 既有交付物 `docs/reference/build-prototype.py`（真实落地图解）、`docs/corpus/character-patterns/ANALYSIS.md`（子分析）。
- 结论先行：**人物→图解是一次有损编译，图解→人物是一次不完全还原**。还原度可检验、可验收，但存在结构性不可还原项；预设必须把「特征层提取」与「还原度自检」做成显式步骤（见第 4 节与 `bundles/gummy-diagram-preset/cordis.patch.yml`）。

---

## 1. 人物 → 图解：信息怎样被编译

### 1.1 两层结构：底模共享 + 特征差异

语料给出的最重要事实是：**人物玩偶图解 = 素体底模（共享）+ 特征层（差异）**。

- [character-patterns/013] Crochethea 的 Q 版素体被作者明言是「所有动漫人物的共用底模，换色+加发+加配件即变人物」；
- [softcandy/001] 软糖体通用主体 R1–R12（肤色环形起针的圆胖胶囊身，R9 用 BLO + 爆米花针 B 一次长出手脚）是同一段图解，哪吒换深棕线、敖丙换蓝线，加上各自的发型/马甲/龙角小件，就成了两个角色；
- [character-patterns/003/012] 欧美素体（doll base）同样只到「头、身、四肢 + 装配说明」为止，脸与发型留给创作者。

也就是说，**素体层几乎不含身份信息**（它只需要肤色），人物的可识别性全部落在特征层：发帽+发片、发色、服装色块、标志性配件（礼帽、龙角、耳机、马甲）、五官配色。这与我们 toySpec 的 `role` 分工（skin/hair/main/accent/eye/blush）天然同构——`role=skin` 是底模，其余 role 是身份。

### 1.2 典型部件清单与装配序

按语料归纳（详见 character-patterns/ANALYSIS.md 第 1 节）：

- 部件三层：**素体层**（头、身体+脖、2 臂、2 腿）→ **特征层**（发帽+发片/刘海、安全眼+刺绣五官）→ **服装配件层**（衣裙裤帽、小件）；小型人物玩偶共 8–14 个缝合级部件。
- 装配序的公共规律：**承重与不可逆步骤在前（塞棉、封口、封头前装安全眼），识别性特征在后（头发、服装、配件），后处理最后（色粉腮红、藏线头）**。
- 定位靠坐标：「手臂缝到身体第 56 圈」「眼在第 7~8 圈」——即装配信息是**圈号坐标**，这正对应我们 `buildOrder` 与 `attachTo` 的表达。

对照本仓库 `characters/芙宁娜/toyspec.json`：9 部件（head/hair-cap/bangs/body/hat/hat-top/arm/leg/eye）+ 12 条 buildOrder，与上述公共序逐条吻合（先头→发帽→刘海→帽→躯干→臂→腿→五官→后处理），说明**我们已按业界公共结构建模**，缺失项只有「刺绣嘴/眉」与「腮红后处理」两处装饰级信息（部分被 contract v1.1 的 decor/loop 覆盖）。

### 1.3 信息损失点：人物→图解丢了什么

综合 character-patterns/ANALYSIS.md 的 12 条损失表与本仓库实测，损失集中在三类：

**A. 连续量 → 离散量（量化损失）**
1. 颜色：渐变/环境色/瞳孔高光 → ≤8 个离散线色 + 换色圈（我们的 palette 上限就是这条工艺约束的编码）；
2. 比例：真人 1:7 头身 → Q 版 1:1~1.2（softcandy 摘要级证据：3 头身最能表现动态）；
3. 细节尺寸：低于「1 针」的细节（睫毛、logo、瞳孔纹）必然丢失——8–14cm 玩偶 1 针 ≈ 4.5mm（我们 gauge 2.2 针/cm 下 1 针 = 4.5mm，正是这个地板）。

**B. 3D 视觉 → 可钩实现性（结构过滤）**
4. 写实面部：睫毛改刺绣或省略，表情只能固化一种（淘宝百科 007 原文）；
5. 多层服装/铠甲接缝 → 合并为色块拼接；褶皱只能用外半针留针模拟（我们的 loopRounds/blo 正是这个手段）；
6. 材质：皮肤/金属/皮革全部统一为线圈纹理；
7. 姿态与透视：只剩静态对称站姿——选图阶段就要求「正面平视、轮廓完整」（007 与英文 ArtPatt [011] 的要求一致，中外互证）；
8. 可动/悬空结构：PP 棉不支撑，除非加骨架（本引擎不建模骨架，属已知边界）。

**C. 图解文本层 → 传播介质（编码损失）**
9. 中文圈主流图解是**一张 JPG 长图，零文本**（017 初音未来样本），机器不可解析；
10. 字母类图解受译者个人习惯影响、常有省略，「信息不全会影响完成率」（001 原文）；
11. 装配段精度天然低于逐圈段（英文图解的 Assembly 多为文字+照片）。

**行业侧验证**：来图定制的验收标准只要求核对「轮廓比例与配色」，明确放弃像素级还原（007）——因为那部分信息在编译时已被合法丢弃。这给了我们一个**合理的还原度目标定义**。

### 1.4 三种表达体系与我们的取舍

[softcandy/002 = character-patterns/001] 给出三分格局：

| 体系 | 地区 | 写法 | 可解析性 |
|---|---|---|---|
| 文字类 written | 欧美 | `R1: (sc, inc) x6 (12)` 括号带总针数 | 高（可直接结构化） |
| 符号类 symbol chart | 日本 | 图形符号，从右向左 | **无文本层**，自动化盲区 |
| 字母类 X/V/A | 中国 | `R2: V,3X,3V,3X,2V` | 高（文法极简，但译者方言） |

我们的契约 §1（X/V/A/T/F/W/M/CH/SL/K）属于字母类，但做了两件业界普遍没做的事：**① 每圈带守恒校验（R1–R9）；② 记号文法唯一化（重复体倍数、换线/装饰显式声明）**。语料证明业界的痛点恰是「无校验、有省略」——001 说省略降低完成率，002 强调英文靠括号总针数自检——我们的 validate-chart.mjs 就是把这条自检做成了机器强制。

## 2. 图解 → 人物：能否还原？

### 2.1 两个实证案例

**案例一：哪吒/敖丙软糖体（同一份图解，两个角色）**
softcandy/001 的通用主体 R1–R12 **单独存在时不含任何身份**——只给「一个圆胖胶囊素体」。还原出角色靠的是差异包：换线颜色（深棕 vs 蓝）、发型针法（黑发双髻 vs 蓝发+龙角）、马甲颜色。**结论：图解→人物的还原键是「底模 + 差异包」，只有底模时还原失败（对应 N 个角色）。**

**案例二：芙宁娜 chart.json 的逆向读取（本仓库实测）**
对 `characters/芙宁娜/chart.json` 只读 chart、不看照片，可恢复：

| 可恢复 | 依据 |
|---|---|
| 发色银白 #E8F4F8、瞳色水蓝 #3D8ED4、服色深蓝 #1A2B5C、金色点缀 | palette 带 role 语义 |
| 有礼帽、有刘海、有发帽 | 部件 id + shape |
| 比例与尺寸（14cm、头 6.5cm、1:1.2 Q 版） | spec.heightCm + shape 直径 |
| 装配顺序与全部针数 | buildOrder + rounds |

| 不可恢复 | 缺失原因 |
|---|---|
| 表情（嘴、眉、腮红位置） | chart 无对应部件，只有 eye |
| 具体身份「这是芙宁娜」 | 名字仅是标签，无 IP 校验；靠配色+礼帽**联想**而非确证 |
| 姿态、刺绣细节、绝对佩戴位置 | 装配坐标只有圈号，无角度/朝向 |
| 原始照片的任何连续量 | 已被量化丢弃（§1.3 A 类） |

**结论：还原度分三级。** ① 结构级（部件/针数/尺寸）——**完全可还原**，chart 是无损的；② 识别级（配色、发型轮廓、标志性配件）——**可还原到「能让熟悉该角色的人认出来」**，这正是行业验收标准（轮廓比例+配色）；③ 肖像级（表情、细节、神态）——**结构性不可还原**，信息在编译时已丢弃，任何更忠实的图解都做不到。

### 2.2 还原度的可操作判据（图解→人物自检）

由 §1.1 与案例二可推出一个可执行的自检：**只看 chart/toySpec，回答「特征层的 N 个决定性特征是否都在」**：

1. 调色板中 hair/main/eye role 齐备且与照片的决定性色一致（photo-to-toy 技能的 3–6 个决定性特征）；
2. 标志性配件有独立部件（帽、角、耳机、马甲……角色没有的不算）；
3. 头身比与尺寸落在 Q 版约定内；
4. 五官（眼）与表情件（若角色以表情为卖点）存在；
5. 反向问一句「把这个 chart 给陌生人看成品，他能否说出这是谁」——不能则回到 ① 补特征。

这五问就是「图解是否能还原人物软糖」的验收问题，也是预设交付前必须自答的问题（已写入预设 persona，见 §4）。

### 2.3 从图解反推「它描述的是什么人」——能力边界

| 输入形态 | 可推断 | 不可推断 |
|---|---|---|
| 结构化 chart（我们的产物） | 部件、比例、配色语义、装配序 | IP 身份、表情、姿态 |
| 中文字母类文本图解（003 小兔子 R1–R67） | 结构可完整重建 | 颜色/身份通常不在文内，需图或换线注记 |
| 英文 written（002/003） | 结构 + 括号总针数可校验 | 同上 |
| 符号图 / JPG 长图（017） | **需要 OCR/读图管线才能进任何自动流程** | 当前文本抓取全盲 |

## 3. 对本项目的含义（差距清单）

1. **✅ 已对齐**：两层结构（toySpec 部件 role 分工 ≈ 底模+特征层）；装配圈号坐标（buildOrder/attachTo）；离散化上界（≤8 色、1 针地板、Q 版比例）；逐圈守恒自检强于业界（业界只靠括号总针数人工数）。
2. **△ 需显式化**：「特征层提取」与「还原度自检」目前只隐含在 photo-to-toy 技能里，预设 persona 应把它们变成交付前的**规定动作**（保留了什么/丢了什么 + 五问自检）。
3. **△ 装饰级信息**：嘴/眉/腮红类表情件在 toySpec 里没有稳定表达（Furina 只有 eye），contract v1.1 的 decor 已开接口，预设应提示模型把「以表情为卖点的角色」落到 decor。
4. **△ 记号方言**：语料里出现 B（爆米花针 5F）、BLO 与 X 连写、`倒2回钩` 等中文惯用写法，与契约 §1 不同——**解析他人图解时必须先归一到契约记号**，不可把方言直接带进 chart。
5. **○ 已知盲区**：图片型图解无文本层，进语料需读图管线；不阻塞当前链路（本项目从照片出发，不解析网络图解）。

## 4. 「软糖图解」预设的优化方向（本次落地）

依据 §1–§3，对 `bundles/gummy-diagram-preset/cordis.patch.yml` 的 persona 做如下增强：

1. **工作流插入 ①.5「特征层清单」**：读照片后先列「底模共性 + 3–6 个决定性特征（发色发型/服装色块/标志配件/表情）」，逐项决定进 toySpec 的哪个部件与 role；
2. **工作流追加 ④「还原度自检」**：交付前只看 toySpec/chart 回答 §1.2 的五问，说明「成品能否被认出是谁」，并把不可还原项（表情细节等）作为已知损失向用户交代；
3. **语料即参考**：提示可在需要结构参照时查阅 `docs/corpus/`（两目录 INDEX.md 与 character-patterns/ANALYSIS.md），尤其是装配公共序与 12 条损失表；
4. **记号归一约束**：引用他人图解时先归一到契约 §1 记号再进引擎；
5. **表情件默认策略**：以表情为识别点的角色，用 decor 表达嘴/眉/腮红，缺省则明确告知用户已省略。
